# Grindset v1.6.0

- README rewritten around current installation, features, setup, privacy and honest reliability boundaries. Removed stale v1.3 status and contradictory signing guidance; detailed evidence remains in linked guides.
- Optional **Settings > Budget warnings**, off by default. At 80% of an activity's daily shared budget, show an in-app heads-up and request a system notification where permitted. Warnings use confirmed, union-accounted usage and the account timezone, not estimated future activity.
- Each activity warns once per account day, persisted across restart. Multiple newly near-limit activities share one summary notification. Already reached limits do not trigger a late pre-limit warning.
- Budget warnings do not enable tracking, alter limits/blocking, change profiles/schedules or interfere with completion alarms. Android requests notification permission only, never exact-alarm permission for this feature.
- Denied/failed notification requests preserve on-screen warnings. They are not retried every collector tick. Native previews with `--no-alerts` remain on-screen only.

All five build/verification jobs passed for source `5ecb2b6` in run `43710707316`. The signed Android artifact retains the existing release certificate (`e5cd43267649b0cda8082dac47eab1332c1d826f9308d3ddbe503df57cf9ac38`). This verifies signing continuity, not Play Protect approval.

Budget and notification tests cover threshold boundaries, overlap/day clipping, opt-in, persistence/restart, once-per-day behavior, failure fallback, a separate notification ID and preservation of the completion alarm. The actual notification SDK is exercised through a mocked OS channel; visible delivery and physical Android/OEM reliability are not newly certified. Existing data, authentication, signing keys and package/storage IDs are retained.

## Publication hold: reported Android installation block

The owner reports Google Play Protect preventing Android download/installation. The exact warning, stage and affected APK are not yet confirmed, so this has not been reproduced or diagnosed. Public v1.6 publication/feed promotion is paused pending those details; this build is not claimed to fix that block. Do not disable Play Protect or change package/signing identities to work around it. Google's [warning guidance](https://developers.google.com/android/play-protect/warning-dev-guidance) distinguishes scan prompts, sensitive-permission blocks and harmful-app classifications; [developer verification](https://support.google.com/android/answer/17065026?hl=en) is a separate process. Follow the applicable official review/verification route only after confirming the actual message.

Read-only checks of the actual v1.5 APK (versionCode 2050) and v1.6 artifact (2051) confirm identical declared permissions and an `AppBlockingService` guarded by `BIND_ACCESSIBILITY_SERVICE`. Both compiled Accessibility configurations set `canRetrieveWindowContent=false` and `canPerformGestures=false`, subscribe only to window-state changes and do not declare `isAccessibilityTool=true`. Neither APK declares SMS, contacts, camera, microphone or notification-listener access. The inspected blocking implementation reads package identifiers, presents a restriction overlay and exposes an explicit Go home action; it does not traverse screen contents or dispatch gestures. This is a bounded configuration/source check, not a whole-app security certification.

Google explicitly lists Accessibility declarations in its internet-sideloading sensitive-permission block criteria, so these APKs meet that documented permission/source condition even when the optional service has not been enabled. The budget feature adds no new Android permissions. This supports a possible permission-based block, but does not establish the phone's actual classification. `adb devices -l` found no connected device, so the reported Play Protect verdict could not be reproduced. Google's [Play Protect appeal form](https://support.google.com/googleplay/android-developer/contact/protectappeals) requests the affected package, APK SHA-256, contact email and supporting information. Do not submit a speculative classification appeal or upload artifacts to third-party scanners without confirming the warning and the owner's consent.
